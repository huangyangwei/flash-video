# Proposal: add-live-detector

## Why

抢码场景里，主播开播时机不定，用户需要反复手动刷新房间页、抓 flv 地址、粘贴播放——开播到出画面的链路里全是人工环节。实测（2026-09-09）抖音房间页 `https://live.douyin.com/<roomId>` 一次 GET 即返回开播状态（内嵌 `"status":2`）和签名 flv 地址（`flv_pull_url`），无需签名/反爬对抗。因此"检测开播"与"拿流地址"是同一个请求，全自动闭环（开播即自动出画面）的成本远低于预期，值得推翻 CLAUDE.md 中"明确不做自动抓流"的既有决策。

## What Changes

- 播放页新增监测面板：**在网页上输入直播间链接与轮询间隔、一键开关**；轮询引擎内嵌 vite dev server（Node 侧，规避 CORS），开播跳变沿取到 flv 地址后**同一页面自动开播**，全链路不经命令行
- 另保留 `npm run watch` CLI 备用入口（房间链接交互/参数输入、深链唤起），与页面监测共用同一套纯逻辑
- 轮询失败熔断退避：请求失败/解析失败时自动退避重试，防止高频轮询触发风控（安全阈值由用户通过自定义间隔校准，spike）
- 播放页支持 `?url=<flv>` 深链参数自动开播，跳过手动粘贴
- 播放页开播瞬间拉流失败（状态已翻、CDN 流未就绪）从"提示重贴地址"改为自动重试退避（2s/4s/8s × 3 次），仍失败才回落到人工提示
- 手动粘贴流程原样保留，作为页面格式变化时的兜底
- **约束修订**：CLAUDE.md"明确不做自动抓流"改为"自动抓流可用，但手动粘贴保留为兜底"

## Capabilities

### New Capabilities

- `live-detection`: Node 轮询脚本行为——房间页轮询、开播判定、flv 地址提取、自定义轮询间隔、失败熔断退避、深链唤起播放页
- `auto-start-playback`: 播放页深链自动开播——`?url=` 参数处理、地址校验、自动开播与失败自动重试

### Modified Capabilities

- `low-latency-playback`: 看门狗行为变化——连接即失败（非缓冲停滞）时不再直接提示重贴地址，先自动重试退避，重试耗尽才回落人工提示（delta spec 到时以主 spec 现状为准）

## Impact

- 新增 `watch.js`（或 `scripts/watch.mjs`）+ `npm run watch` script；Node 21 自带 fetch，零新依赖
- `src/player.js`（或 main.js）：解析 `?url=` 参数、自动重试逻辑
- 测试：轮询解析（内嵌 JSON 提取状态/地址）、间隔与退避决策为纯逻辑，纳入 `node --test`
- 风险：解析依赖抖音页面私有内嵌格式（随时可变，靠手动粘贴兜底）；轮询频率的风控安全阈值未知，需真实使用校准（spike）；离播页面形态未采样（spike，待主播下播时抓样本）
