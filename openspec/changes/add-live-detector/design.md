# Design: add-live-detector

## Context

实测验证（2026-09-09，房间 134525032676 直播中）：

- `GET https://live.douyin.com/<roomId>`，浏览器 UA，一次请求即 200，响应头直接 `Set-Cookie: ttwid`，无需 `__ac_nonce` 两步舞，无需任何签名
- 1.2MB HTML 内嵌 JSON（`self.__pace_f.push` 系列）包含：转义的 `"status":2`（直播中；已知枚举 4=结束）与 `stream_url.flv_pull_url` / `web_stream_url.flv_pull_url`（多清晰度，URL 带签名与 `expire`）
- `webcast/room/web/enter/` API 返回空体（需 a_bogus 签名）——不可用，死路，放弃

约束：web 播放页 fetch douyin.com 必被 CORS 拦死，轮询必须跑在 Node 侧；Node 21 自带 fetch，零新依赖。方案 A（深链唤起）已获用户确认，轮询间隔用户可自定义是硬需求。

## Goals / Non-Goals

**Goals:**

- 开播到出画面的全链路无人值守：轮询 → 判定 → 提取地址 → 唤起播放页 → 自动开播
- 轮询间隔、房间号、播放页 origin 全部可配置（CLI 参数 + 默认值）
- 失败行为可预期：退避重试、不崩溃、不误报、不重复唤起

**Non-Goals:**

- 不做常驻服务/信箱（vite plugin 方案 B 已否决）；每场开播弹一个新标签页是接受的形态
- 不做签名对抗、代理池、多房间监控
- 不改 OCR handoff 计划（`add-ocr-handoff` 另立，未来由 C++ 工具统一统筹后可演进替换本方案的深链唤起，见 Open Questions）
- 下播后的播报/通知（只关心开播）

## Decisions

### D1. 轮询载体（修订）：内嵌 vite dev server 的插件，CLI 脚本降为备用

初版为独立 Node CLI 脚本 + 深链唤起。用户需求修订（配置要在网页上、不想碰命令行）后改为：轮询引擎做成 vite plugin 挂在 dev server 的 `/__watch/api`（dev server 本来就是常驻 Node，天然无 CORS、零新增进程），播放页面板 POST 配置 / GET 状态，开播时同一页面直接自动开播——不再需要深链弹新标签页。`scripts/watch.mjs` 保留为页面未打开时的备用入口，与插件共用 `src/lib` 的同一套纯逻辑（解析/跳变沿/退避）。约束修订说明：这不算引入"服务器"——没有新增监听端口，只是给本就运行的 dev server 加了本地接口。

### D2. 判定与提取：解析页面内嵌 JSON，不做任何 API 调用

正则/切片提取 `"status":2` 与 `flv_pull_url`（先取 FULL_HD1，退化到第一个值）。理由：API 需签名已验证死路；页面格式虽是私有格式，但解析器按宽容策略写（找不到字段按解析失败处理，走退避），且手动粘贴永远保留为兜底。离播页面形态未采样（spike，见 Risks）——首版以"找不到 status 字段 = 未开播或解析失败"处理，抓到样本后定稿。

### D3. 跳变沿触发：脚本内存保存上一轮状态，仅在 未开播→直播中 时唤起一次

不做持久化：重启脚本视为重新观察跳变沿，若当前已直播则立即唤起一次（符合直觉：刚启动就想看就开）。唤起动作 = `start <深链>`（Windows `child_process.exec` 或 `open` 语义），深链 origin 默认 `http://127.0.0.1:5173`，`--origin` 可覆盖。**房间指定（需求修订）**：用户每次运行时手动给房间——`--room` 接受完整直播间链接（正则提取路径数字）或纯房间号；未提供时启动交互询问（node:readline，回车回落默认房间）。想同时盯多个房间 = 跑多个 watch 实例（单人自用，不做进程内多房间调度）。

### D4. 轮询间隔与退避：间隔用户可配（默认 15s），退避独立于间隔

- 正常轮询：严格按 `--interval`（默认 15s，用户明确要求可自定义）
- 失败退避：失败后延迟 = min(interval × 2^连续失败次数, 300s)，成功后清零。退避是防风控的熔断器，与"正常时多快"正交
- 提取纯逻辑（间隔计算、退避计算、状态跳变判定、内嵌 JSON 提取）为纯函数，进 `node --test`

### D5. 播放页自动重试：连接失败退避 2s/4s/8s × 3 次，UI 显示重试进度

只作用于**初始连接**（含手动粘贴与深链两个入口）；播放中段的断流仍走现有 15s 看门狗 → 人工提示路径（那个场景重试无意义，地址多半已过期）。实现位置：`src/player.js` 的连接错误处理分支。重试次数/退避序列为纯逻辑，进测试。

### D6. 深链传参：`#/?url=` hash 参数，播放页启动时读取一次

flv 地址含 `&` 等字符，唤起前 MUST `encodeURIComponent`；播放页读取后先做与手动粘贴相同的校验再走播放。参数缺失 = 现状不变。不用 localStorage/信箱，避免状态同步问题。**实测修正（任务 3.1 验证中发现）**：查询串形式 `/?url=http%3A%2F%2F...` 会被 vite dev 5.4.21 的安全补丁做 fs 路径校验直接 403，故改用 hash 传参——fragment 不经过服务器，dev/静态托管通吃。

## Risks / Trade-offs

- [轮询触发风控，连累本人浏览器看直播] → 间隔可配 + 失败退避熔断；默认 15s 偏保守；spike：用户日常使用中观察，被拦了调大间隔。页面格式或风控突变时，手动粘贴流程不受影响
- [下播页面形态未知，解析器首版可能误判] → 宽容策略：找不到明确状态字段一律按"未开播/解析失败"，宁可漏报不可误报（误报会弹浏览器打扰）。spike：主播下播时抓样本定稿
- [页面格式改版，检测静默失效] → 解析失败在控制台持续可见（用户在场能看到）；spec 明确解析失败不误报开播
- [flv 地址在检测到开播的瞬间可能拉不动] → 播放页 3 次退避重试（D5）；仍不行用户手动粘贴兜底
- [每场开播弹新标签页，烦] → 接受（方案 A 的已知代价）；未来 OCR 工具常驻后可演进

## Migration Plan

纯增量：新增 `scripts/watch.mjs` + npm script，`src/player.js` 加深链读取与重试分支。回滚 = 删文件/还原 diff，无数据迁移。CLAUDE.md 的"明确不做自动抓流"约束随本 change 归档时更新。

## Open Questions

- OCR handoff（`add-ocr-handoff`）落地后，watch 脚本的唤起动作是否同时 POST 给 C++ 工具（接口契约在那边定，本 change 不做，但 D3 的唤起动作留了单点，容易扩展）
- 默认轮询间隔 15s 是否合适——交给用户使用中校准（spec 已保证可自定义）
