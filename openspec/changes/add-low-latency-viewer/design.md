# design — add-low-latency-viewer

## Context

单人自用工具（见 proposal.md - Why）。无后端、无多观众；唯一输入是用户手动从抖音页面抓取的 `.flv` 地址。项目当前为空白，无既有技术栈约束。上游（抖音推流编码、CDN、TCP 传输）完全不受控——设计能优化的只有播放器一侧。

## Goals / Non-Goals

**Goals:**
- 端到端延迟压到 ~1.5s（地板 ~0.5-1s，受上游 GOP 制约）
- 追帧行为全参数可调、即时生效
- 断流（地址签名过期）体验明确：提示 + 重贴 + 从直播边缘恢复

**Non-Goals:**
- 不做自动抓流/地址提取（用户手动 DevTools 抓取）
- 不做服务器、多观众、录屏、弹幕等任何扩展功能
- 不做 TCP 传输层或协议级优化（mpegts.js 走 HTTP 即可）

## Decisions

### D1: 播放核心用 mpegts.js，纯前端 + MSE
选 mpegts.js（flv.js 作者后继项目）：FLV over HTTP → MSE，浏览器原生支持，无需编译播放器内核。
- 备选 mpv/VLC 等本地播放器：配置 1 分钟即可用，但无法做自定义追帧 UI 与参数化，也不成"项目"。弃。
- 备选 hls.js：抖音 Web 主分发是 FLV，HLS 切片延迟天然高。弃。

### D2: 缓冲策略 = 基本不扩，卡了就跳
普通播放器"慢扩快缩"是为了流畅；抢码场景反过来——**宁可花屏/卡一下，绝不攒缓冲**。因此：
- `enableStashBuffer: false`、`stashInitialSize: 384`（mpegts.js 官方低延迟推荐值）
- 不实现渐进式缓冲收缩；水位治理完全交给追帧模块（变速回吐 + 超限跳帧）
- 备选"自适应 jitter buffer"：实现复杂、单人收益低，跳帧兜底已覆盖其价值。弃。

### D3: 追帧三旋钮 + 边缘由跳帧承担 + 默认静音
用户明确"只在乎画面，不在乎声音"，因此**默认静音**——单 video 元素 MSE 下 `playbackRate` 同时作用于音视频的难题就此消解，变速不再需要任何音频补偿：
- 水位 < 变速阈值：1.0x 正常播放
- 变速阈值 ≤ 水位 < 跳帧阈值：以倍率（1.05~2.0x）追，上限只受画面可感知快放约束（原 1.5x 上限为护耳而设，已随静音取消）
- 水位 ≥ 跳帧阈值：seek 到 buffered 末端（最新关键帧），清历史缓冲
- 更激进的需求由"降低跳帧阈值"表达，而非提高倍率
- 用户可通过播放器控件手动取消静音（此时变速会带轻微语速加快、音调不变）

### D4: 延迟可量化（先用相对对比，SEI 时间戳为可选增强）
抖音 Web 播放器无公开延迟指标。验收手段：
- 主手段：同房间双开（本播放器 + 抖音 Web 页），以"画面内容时间差"人工对比
- 可选增强：解析 FLV tag/SEI 中的推流时间戳计算绝对延迟；抖音是否写入 SEI 时间未验证，列为开放问题，不阻塞主线

### D5: 地址生命周期 = 手动重贴
地址签名过期无规律可保证，自动续期需要复刻抓流签名逻辑（越界）。断流时：mpegts.js error 事件 → 停止播放 → 展示"地址已失效"提示 + 粘贴框。重贴后新建播放实例，天然从直播边缘开始。

## Risks / Trade-offs

- [浏览器 tab 后台节流导致 buffer 堆积] → 前台化提醒 + 醒目延迟指示；追帧模块在回到前台后自动收敛（跳帧兜底）
- [取消静音后变速会有可感知的语速加快] → 默认静音已规避；手动取消静音的用户可自行调低倍率
- [跳帧命中处花屏/卡顿] → FLV 关键帧间隔即上游 GOP（~1-2s），一跃最多"卡一下"，符合抢码优先级
- [抖音改 FLV 分发方式（如转 QUIC/加密）] → 本方案依赖公开 .flv 地址形态；若上游变化需重新评估抓流可行性（超出本 change 范围）

## Open Questions

- 抖音 FLV 流是否携带 SEI 绝对时间戳（决定 D4 增强手段是否可行）——实现期验证，不影响架构
